Build a complete full-stack mock hotel-booking web application called “LikeHome.” LikeHome should be a simplified Hotels.com-style application designed as a semester project for third-year college students.

Before writing code, review every requirement below and create a short implementation plan. Build the application in manageable phases. After each phase, run the application, check for errors, and confirm that the completed features work. Do not claim the project is complete until the acceptance checklist at the end passes.

# 1. Project goals

The application must allow customers to:

1. Create an account and log in.
2. Browse sample hotels.
3. Search for hotels by name or location.
4. select check-in and check-out dates.
5. Filter and sort hotel results.
6. View hotel and room details.
7. Create a reservation.
8. View all personal reservations.
9. Change an existing reservation.
10. Cancel a reservation.
11. Make a test payment or simulated payment.
12. Receive a cancellation charge when applicable.
13. Earn reward points.
14. Redeem enough points for a free stay.
15. Be prevented from creating overlapping reservations.

This is a mock academic application. Do not connect it to real hotel systems or process real money.

# 2. Required technology stack

Use the following stack:

* TypeScript as the programming language.
* Next.js using the App Router.
* React for the user interface.
* Tailwind CSS for styling.
* Next.js server actions or route handlers for backend operations.
* Supabase PostgreSQL for the database.
* Supabase Authentication for signup, login, logout and sessions.
* Stripe Test Mode for payment demonstrations.
* Replit for development and previewing.
* The project must be compatible with GitHub.
* Use manual QA checklists as the main testing method.

Do not create a separate Express backend. Keep the frontend and backend in one Next.js project.

Use Supabase Authentication.

Implement:

* Login.
* Logout.
* Session persistence.
* Protected booking, checkout, rewards and account pages.
* Automatic profile creation after signup.

Apply Supabase Row Level Security policies so:

Never trust a user ID, price, total, reward balance or reservation status submitted by the browser.

# 8. Reservation rules

All reservation rules must be checked on the server.

A reservation is invalid when:

* Check-out is not after check-in.
* Check-in is in the past.
* Guest count is less than one.
* Guest count exceeds room capacity.
* The selected room does not have available inventory.
* The same user already has a confirmed reservation whose dates overlap the requested dates, even if it is at a different hotel.

Use this date-overlap rule:

A new reservation overlaps an existing reservation when:

newCheckIn < existingCheckOut
AND
newCheckOut > existingCheckIn

Back-to-back reservations are allowed. For example, one reservation may end on the same day another begins.

Availability checks and reservation creation must occur safely so two users cannot take the final available room at the same time. Use a database transaction, database function or another safe server-side method.

Never depend only on frontend validation.

# 9. Pricing rules

Calculate prices on the server.

Use:

numberOfNights = checkOutDate - checkInDate

subtotal = roomPricePerNight × numberOfNights

The client may display an estimate, but the server must load the current room price and calculate the final amount again before confirming the reservation.

Format all money as U.S. dollars.

# 10. Cancellation policy

Since the project requirements do not provide exact cancellation rules, implement these configurable demonstration rules:

* Cancellation more than 48 hours before check-in: no cancellation charge.
* Cancellation within 48 hours of check-in: charge 20% of the reservation total.
* Cancellation after the check-in date: cancellation is not permitted through the website.

Store these values as named configuration constants so the team can change them later.

Show the policy clearly before the user confirms a booking and again before cancellation.

# 11. Reward-point rules

Implement these configurable demonstration rules:

* Users earn 1 point per dollar spent.
* Points are awarded only after a reservation is marked completed.
* Cancelled reservations do not earn points.
* Redeeming 1,000 points provides one free night.
* A free-night reward cannot exceed the selected room’s nightly rate.
* Record every points change in reward_transactions.
* Never allow the reward balance to become negative.

Store these rules as configuration constants so they can be changed after Product Manager approval.

For the academic demo, provide a safe development-only method to mark a sample reservation completed so reward points can be demonstrated. Do not expose this control in production.
